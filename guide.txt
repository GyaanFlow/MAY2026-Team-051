1. PROJECT OVERVIEW
========================================================================

This is a Flask + Flask-RESTful + JWT based REST API for a Library
Membership Management System, now extended with a Booking and Seat
Management module. It has three user roles:

  - Admin   : manages staff, membership plans, approves/rejects memberships
  - Staff   : registers new students, views student profiles
  - Student : views/edits own profile, resets password, books seats

Tech stack:
  - Flask 3.0.3
  - Flask-RESTful 0.3.10
  - Flask-SQLAlchemy 3.1.1
  - Flask-JWT-Extended 4.6.0
  - Werkzeug 3.0.3
  - Flask-CORS 4.0.1
  - SQLite (default local database, file: app.db)

2. PROJECT STRUCTURE
========================================================================

seProject/
|-- app.py                  -> creates Flask app, registers all routes, seeds data
|-- config.py                -> app config (secret keys, database URL, JWT expiry)

4. AUTHENTICATION FLOW
========================================================================

Every route except /auth/login requires a Bearer token.

Step 1: Login
    POST /api/auth/login
    Body (JSON):
    {
      "username": "admin",
      "password": "admin123"
    }

    Response:
    {
      "access_token": "xxxxx.....",
      "user": { ...user fields... }
    }

Step 2: Use token on every other request
    Header:
    Authorization: Bearer <access_token>

Token expires after 8 hours.

Roles embedded in JWT: role = Admin / Staff / Student.
Decorators in utils.py:
    admin_required           -> Admin only
    staff_or_admin_required  -> Staff or Admin

Booking APIs (seats.py, bookings.py) only require jwt_required() -
any logged-in role (Admin, Staff, Student) can check availability and
book seats. Modify/cancel additionally check that the caller either
owns the booking or is Staff/Admin.

5.1 AUTH

5.7 ADMIN MEMBERSHIP MANAGEMENT (Story 1.2 - Admin only)
GET    /api/admin/memberships/pending
GET    /api/admin/memberships  (optional ?status=Active)
POST   /api/admin/memberships/<membership_id>/approve
POST   /api/admin/memberships/<membership_id>/reject
PUT    /api/admin/memberships/<membership_id>
    Body (any of): { "plan_id": 2 } or { "extend_days": 30 } or { "membership_expiry": "2026-12-31" }

5.8 SEAT AVAILABILITY (Story 3.1 - any logged-in user) - NEW
GET    /api/seats/availability?date=YYYY-MM-DD&start_time=HH:MM&end_time=HH:MM
    Returns: list of free seats for that date/time slot
    Errors: 400 missing/invalid params, 400 start_time >= end_time

5.9 ADVANCE BOOKING (Story 3.2 - any logged-in user) - NEW
POST   /api/bookings
    Body: { "seat_id": 1, "date": "2026-08-10", "start_time": "10:00", "end_time": "12:00" }
    Returns: 201 with booking object including auto-generated checkin_code
    Errors: 400 missing fields/bad format, 404 seat not found/inactive,
            409 seat already booked for that slot

5.10 BOOKING MODIFICATION (Story 3.3 - owner, Staff, or Admin) - NEW
PUT    /api/bookings/<booking_id>
    Body (any of): { "date":"", "start_time":"", "end_time":"" }
    Errors: 400 bad format/invalid time range, 403 not authorized,
            404 booking not found, 409 new slot clashes with existing booking

POST   /api/bookings/<booking_id>/cancel
    Body: none
    Returns: 200, booking status set to "Cancelled", seat freed
    Errors: 400 already cancelled, 403 not authorized, 404 not found

7. COMMON ERRORS AND FIXES
========================================================================

"Email is required" even though sent -> set Content-Type: application/json,
    Body tab set to JSON not Text.
401 Unauthorized on every request -> token missing/expired/no "Bearer " prefix.
403 not allowed -> wrong role's token used for that route, or trying to
    modify/cancel someone else's booking without Staff/Admin role.
sqlite3.OperationalError: no such column/table -> delete app.db, restart server
    (required after adding Seat/Booking models).
ModuleNotFoundError: No module named 'flask_cors' -> pip install -r requirements.txt.
git push rejected (fetch first) -> git pull origin dev, then push again.
409 Seat already booked -> expected behavior when double-booking same
    seat/date/overlapping time - not a bug.

11. WHY THIS STRUCTURE IS USED
========================================================================

The backend uses JSON request bodies with Flask request.get_json(), which
matches how modern frontend apps send API data. Flask-CORS is enabled on
/api/* routes so frontend code running on a different origin can call the
backend without browser CORS issues. Thunder Client is used for testing
because it supports collections, environments, request headers, auth,
and response testing directly inside VS Code.

The booking system checks for overlapping time ranges using the standard
interval-overlap condition (existing_start < new_end AND existing_end >
new_start) rather than exact match, so partial overlaps are correctly
blocked, not just identical time slots.

13. DATABASE SCHEMA (ERD SUMMARY)
========================================================================

TABLE: users
--------------------------------------------------------------------
user_id         Integer PK      auto-increment
username        String(100)     unique, required
password_hash   String(255)     hashed with Werkzeug generate_password_hash
email           String(150)     required
id_type         String(255)     optional
id_number       String(255)     optional
phone           String(20)      optional
role            String(20)      "Admin" / "Staff" / "Student"
status          Boolean         True = active account, False = deactivated

TABLE: membership_plans
--------------------------------------------------------------------
plan_id         Integer PK      auto-increment
plan_name       String(100)     "Weekly" / "Monthly" / "Yearly" (seeded)
duration_days   Integer         used to calculate membership_expiry on approve
price           Numeric(10,2)   set by Admin via PUT /membership-plans/<id>

TABLE: students
--------------------------------------------------------------------
student_id          Integer PK      auto-increment
user_id             Integer FK      -> users.user_id (1-to-1 with a User row)
full_name           String(150)     required
address             Text            optional
membership_status   String(20)      Pending / Active / Rejected / Disapproved
plan_id             Integer FK      -> membership_plans.plan_id (nullable)
membership_expiry   Date            set automatically when Admin approves

TABLE: seats (NEW)
--------------------------------------------------------------------
seat_id         Integer PK      auto-increment
seat_number     String(20)      unique, e.g. "S01"
seat_type       String(50)      e.g. "Standard"
is_active       Boolean         default True, inactive seats hidden from availability

TABLE: bookings (NEW)
--------------------------------------------------------------------
booking_id      Integer PK      auto-increment
user_id         Integer FK      -> users.user_id (who made the booking)
seat_id         Integer FK      -> seats.seat_id
booking_date    Date            the date of the booking
start_time      Time            slot start
end_time        Time            slot end
checkin_code    String(20)      unique, auto-generated on creation
status          String(20)      "Confirmed" / "Cancelled"
created_at      DateTime        auto-set on creation

RELATIONSHIPS
--------------------------------------------------------------------
users (1) ----- (1) students
membership_plans (1) ----- (many) students
users (1) ----- (many) bookings
seats (1) ----- (many) bookings

IMPORTANT: There is currently NO separate "memberships" table - admin
membership routes reuse student_id as membership_id (unchanged limitation,
see section 15). Bookings check overlap using start_time < new_end AND
end_time > new_start, so back-to-back bookings (e.g. one ending exactly
when another starts) are allowed, not blocked.

========================================================================
14. FIELD REFERENCE (WHAT EACH FIELD MEANS)
========================================================================

username           - login identifier, must be unique across all roles
password            - plain text on input only, stored as hashed password_hash
email               - contact email, required for all users
id_type             - type of ID proof submitted (e.g. "Aadhar", "College ID")
id_number           - the actual ID proof number matching id_type
phone               - contact number, optional, no format validation currently
role                - controls access: Admin / Staff / Student (server-set only)
status (User)       - true = can log in, false = deactivated
full_name           - student's display name, required at registration
address             - student's address, optional, free text
membership_status   - Pending / Active / Rejected / Disapproved
plan_id             - links student to a MembershipPlan; can be null
membership_expiry   - calculated as today + plan.duration_days on approval
duration_days       - defines how long a plan lasts once approved
price               - plan cost, editable by Admin only, stored as decimal
seat_number         - human-readable seat label shown to users, e.g. "S01"
seat_type           - category of seat, currently just "Standard" for all
is_active           - false hides a seat from availability without deleting it
checkin_code        - random 8-character code generated per booking, used to
                      verify the student physically checked in (front-desk
                      scan/entry step - not yet wired to a separate endpoint)
booking_date/start_time/end_time - defines the exact reserved slot
status (Booking)    - "Confirmed" (active) or "Cancelled" (freed)

1. membership_id == student_id (unchanged from Epic 1)
2. No password reset via email (unchanged from Epic 1)
3. No refresh token - 8 hour expiry, re-login required (unchanged)
4. No staff reactivation route (unchanged)
5. role is server-controlled, never accepted from client body (unchanged)
6. No pagination on list endpoints (unchanged)
7. SQLite only in dev (unchanged)

NEW (Epic 3 - Booking):
8. No separate check-in endpoint yet
   checkin_code is generated and stored, but there is no
   POST /bookings/<id>/checkin route to actually validate/consume the
   code at the library entrance. This may be a future story.

9. No booking list/history endpoints yet
   There is no GET /bookings (list a user's own bookings) or
   GET /bookings/<id> (view one booking's details) - only create,
   modify, and cancel exist per the given stories. Recommend adding
   these next for a usable frontend experience.

10. No max-booking-duration or advance-booking-window validation
    A user can currently book any seat for any date/time range with no
    limit on how long or how far in advance - confirm with client if
    business rules are needed here (e.g. max 4 hours, book up to 7 days
    ahead only).

11. Overlap check is per-seat, not global
    Two different users CAN book two different seats for the exact same
    time slot - this is intentional (each seat is independent), but
    worth confirming this matches the client's expectation of a shared
    library seating layout.

17. HOW TO PUSH TODAY'S WORK TO GITHUB (STEP BY STEP)
========================================================================

If you built Epic 3 directly on separate feature branches (recommended,
see below), push each branch and open a PR into dev. If you already have
all the Epic 3 code sitting uncommitted on your dev branch, use the
simpler direct-push steps in 17.2 instead.

------------------------------------------------------------------------
17.1 - RECOMMENDED: Push via feature branches (5 PRs)
------------------------------------------------------------------------

Repeat this pattern once per branch:
    feature/booking-models-setup
    feature/seat-availability
    feature/advance-booking
    feature/booking-modification
    feature/booking-cancellation

    git checkout dev
    git pull origin dev
    git checkout -b feature/booking-models-setup
    git add models.py app.py
    git commit -m "add seat and booking models with sample seed data"
    git push -u origin feature/booking-models-setup

    (Open PR on GitHub: base=dev, compare=feature/booking-models-setup)
    (Review, then click Merge pull request)

    git checkout dev
    git pull origin dev
    git branch -d feature/booking-models-setup

Then repeat for each remaining branch, e.g.:

    git checkout -b feature/seat-availability
    git add resources/seats.py app.py
    git commit -m "add real-time seat availability api - story 3.1"
    git push -u origin feature/seat-availability
    (open PR, merge)

    git checkout dev && git pull origin dev
    git checkout -b feature/advance-booking
    git add resources/bookings.py app.py
    git commit -m "add advance booking api with checkin code generation - story 3.2"
    git push -u origin feature/advance-booking
    (open PR, merge)

    git checkout dev && git pull origin dev
    git checkout -b feature/booking-modification
    git add resources/bookings.py app.py
    git commit -m "add booking modification api - story 3.3a"
    git push -u origin feature/booking-modification
    (open PR, merge)

    git checkout dev && git pull origin dev
    git checkout -b feature/booking-cancellation
    git add resources/bookings.py app.py
    git commit -m "add booking cancellation api - story 3.3b"
    git push -u origin feature/booking-cancellation
    (open PR, merge)

    git checkout dev
    git pull origin dev

At the end you will have 5 merged PRs visible in GitHub's Pull Requests
tab (closed/merged filter) as proof of incremental feature-branch work.
