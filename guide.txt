========================================================================
1. PROJECT OVERVIEW
========================================================================

This is a Flask + Flask-RESTful + JWT based REST API for a Library
Membership Management System, now extended with Seat Booking and
Extension Approval. It has three user roles:

  - Admin   : manages staff, membership plans, approves/rejects memberships,
              configures operating hours and seat inventory
  - Staff   : registers new students, views student profiles, handles
              walk-ins, reviews/approves booking extension requests
  - Student : views/edits own profile, resets password, books seats and
              requests booking extensions

Tech stack:
  - Flask 3.0.3
  - Flask-RESTful 0.3.10
  - Flask-SQLAlchemy 3.1.1
  - Flask-JWT-Extended 4.6.0
  - Werkzeug 3.0.3
  - Flask-CORS 4.0.1
  - SQLite (default local database, file: app.db)

|     |-- auth.py               -> login
|     |-- staff.py               -> admin managing staff accounts (Story 1.1)
|     |-- membership.py           -> admin managing membership plans (Story 2.3)
|     |-- profile.py                -> Admin/Staff own profile + password reset (any role)
|     |-- student_profile.py         -> Story 1.4/1.5: student's own profile at /students/me
|     |-- staff_students.py          -> staff registers/views/verifies a student (Story 1.3)
|     |-- admin_memberships.py        -> admin membership approval workflow (Story 1.2)
|     |-- settings.py                 -> admin library settings / operating hours (Story 2.1)
|     |-- seats.py                     -> admin seat inventory (Story 2.2) + real-time
|     |                                   seat availability search (Story 3.1)
|     |-- bookings.py                   -> advance booking, modification, cancellation,
|     |                                   booking history, daily overview, walk-in
|     |                                   admission (Stories 3.2-3.6), and study
|     |                                   session check-out (Story 4.4)
|     |-- extension_requests.py          -> booking extension request/approve/reject

3. HOW TO RUN THE PROJECT (STEP BY STEP)
========================================================================

Step 1 - Install dependencies
    pip install -r requirements.txt

Step 2 - Delete old database if schema changed
    Windows:
        del app.db
    or if it is inside an instance folder:
        del instance\app.db

    You should see:
    " * Running on http://127.0.0.1:5000"
    with no red traceback text.

Step 5 - Default admin login (auto-seeded on first run)
    username: admin
    password: test-password

Step 6 - Default membership plans (auto-seeded)
    Weekly   - 7 days
    Monthly  - 30 days
    Yearly   - 365 days

4. AUTHENTICATION FLOW
========================================================================

Every route except /auth/login requires a Bearer token.

Step 1: Login
    POST /api/auth/login
    Body (JSON):
    {
      "username": "admin",
      "password": "test-password"
    }

    Response:
    {
      "access_token": "xxxxx.....",
      "user": { ...user fields... }
    }

Step 2: Use token on every other request
    Header:
    Authorization: Bearer <access_token>

Token expires after 8 hours.

Roles embedded in JWT: role = Admin / Staff / Student.
Decorators in utils.py:
    admin_required           -> Admin only
    staff_or_admin_required  -> Staff or Admin

5. COMPLETE API REFERENCE
========================================================================

5.1 AUTH
POST   /api/auth/login
    Body: { "username": "", "password": "" }
    Errors: 400 missing fields, 401 invalid credentials, 403 deactivated

POST   /api/auth/reset-password   (any logged-in user)
    Body: { "old_password": "", "new_password": "" }
    Errors: 400 missing fields, 401 old password wrong, 404 user not found

5.2 PROFILE (Story 1.1/general - Admin or Staff only; Students get 403 here)
GET    /api/profile
PUT    /api/profile
    Body (any of): { "email":"", "phone":"" }

5.3 STAFF MANAGEMENT (Story 1.1 - Admin only)
GET    /api/admin/staff
POST   /api/admin/staff
    Body: { "username":"", "password":"", "email":"", "id_type":"", "id_number":"", "phone":"" }
GET    /api/admin/staff/<user_id>
PUT    /api/admin/staff/<user_id>
    Body (any of): { "email":"", "id_type":"", "id_number":"", "phone":"", "password":"" }
POST   /api/admin/staff/<user_id>/deactivate

5.4 MEMBERSHIP PLANS (Story 2.3 - Admin only)
GET    /api/admin/membership-plans
    Lists all plans, including retired ones (check is_active)
POST   /api/admin/membership-plans
    Body: { "plan_name": "Quarterly", "duration_days": 90, "price": 900 }
    Errors: 400 missing/invalid fields
PUT    /api/admin/membership-plans/<plan_id>
    Body (any of): { "plan_name":"", "duration_days":90, "price":300 }
    Errors: 404 not found, 400 invalid field values
DELETE /api/admin/membership-plans/<plan_id>
    Retires the plan (sets is_active=False). Does NOT hard-delete the
    row - students already on this plan (students.plan_id) still
    reference it. There is no "un-retire" route yet (same limitation
    as staff deactivate - see section 15).
    Errors: 404 not found, 400 already retired

5.5 STUDENT SELF-SERVICE (Story 1.4/1.5 - Student only)
GET    /api/students/me
    Returns own profile fields + membership_status/membership_expiry/membership_valid
PUT    /api/students/me
    Body (any of): { "email":"", "phone":"", "full_name":"", "address":"" }

5.6 STAFF STUDENT REGISTRATION & LOOKUP (Story 1.3 - Staff or Admin)
POST   /api/staff/students/register
    Body: { "username":"", "password":"", "email":"", "full_name":"", "address":"", "plan_id": 1, "id_type":"", "id_number":"", "phone":"" }
GET    /api/staff/students/<student_id>
GET    /api/staff/students/<student_id>/verify
    Returns { "status": "", "valid": true/false, "membership_expiry": "" }

5.7 ADMIN MEMBERSHIP MANAGEMENT (Story 1.2 - Admin only)
GET    /api/admin/memberships/pending
GET    /api/admin/memberships  (optional ?status=Active)
POST   /api/admin/memberships/<membership_id>/approve
POST   /api/admin/memberships/<membership_id>/reject      (only from Pending)
POST   /api/admin/memberships/<membership_id>/disapprove  (only from Active)
PUT    /api/admin/memberships/<membership_id>
    Body (any of): { "plan_id": 2 } or { "extend_days": 30 } or { "membership_expiry": "2026-12-31" }

5.8 LIBRARY SETTINGS (Story 2.1 - Operating Hours - Admin only)
GET    /api/admin/settings
    Returns the single library_settings row (open_time, close_time, and
    other library_settings columns - total_seats, no_show_grace_minutes,
    cancellation_period, max_booking_days_ahead, extension_limit_minutes -
    which are still null until the stories that own them are implemented)
PUT    /api/admin/settings
    Body (any of): { "open_time": "09:00", "close_time": "21:00" }
    Times are 24-hour "HH:MM". close_time must be after open_time.
    Errors: 400 bad time format, 400 close_time <= open_time
    A default row (09:00-21:00) is auto-seeded on first app run.

5.9 SEAT INVENTORY (Story 2.2 - Admin only)
GET    /api/admin/seats
    List all seats with seat_type/is_active
POST   /api/admin/seats
    Body: { "seat_number": "A1", "seat_type": "Standard", "is_active": true }
    seat_type and is_active are optional (is_active defaults to true).
    seat_number must be unique.
    Errors: 400 missing/invalid, 409 seat_number already exists
PUT    /api/admin/seats/<seat_id>
    Body (any of): { "is_active": false, "seat_type": "Premium" }
    Changes a seat's active flag and/or type (seat_number is not
    renameable via this route). A seat with is_active=false is excluded
    from booking/availability (this replaced the earlier
    status Available/Maintenance field - see section 15 item 8).
    Errors: 404 seat not found, 400 missing/invalid fields

5.10 SEAT AVAILABILITY & BOOKING (Stories 3.1-3.6 - any logged-in role
     unless noted)
GET    /api/seats/availability?date=YYYY-MM-DD&start_time=HH:MM&end_time=HH:MM
    Lists active seats with no overlapping Confirmed booking in that
    window.
POST   /api/bookings
    Body: { "seat_id": 1, "date": "YYYY-MM-DD", "start_time": "HH:MM", "end_time": "HH:MM" }
    Creates a Confirmed booking for the logged-in user and generates a
    checkin_code. Errors: 400 missing/invalid fields or bad time range,
    404 seat not found/inactive, 409 seat already booked for that slot.
PUT    /api/bookings/<booking_id>
    Body (any of): { "date":"", "start_time":"", "end_time":"" }
    Only the booking's own user, or Staff/Admin, may modify it, and only
    while it is still Confirmed. Errors: 403 not your booking, 400 bad
    fields, 409 new slot clashes with another booking on that seat.
POST   /api/bookings/<booking_id>/cancel
    Sets status to Cancelled, freeing the seat. Same ownership rule as
    PUT above. Errors: 403 not your booking, 400 already cancelled.
GET    /api/students/me/bookings   (Student - own bookings only)
    Full booking history for the logged-in student, newest first,
    each entry annotated with seat_number.
GET    /api/staff/bookings/today   (Staff or Admin)
    Today's Confirmed bookings, earliest first, annotated with
    seat_number/username/full_name.
POST   /api/staff/bookings/walk-in   (Staff or Admin)
    Body: { "student_id": 1, "duration_minutes": 60 }
    Auto-assigns the first free active seat for right now and creates a
    Confirmed booking. duration_minutes optional, defaults to 60.
    Errors: 400 missing/invalid student_id or duration, 404 student not
    found or no seats configured, 400 membership not Active, 409 no free
    seat available right now.

5.11 EXTENSION APPROVAL & SEAT ALLOCATION (Story 3.7)
POST   /api/students/me/bookings/<booking_id>/extension-request  (Student, own booking only)
    Body: { "requested_end_time": "HH:MM" }
    Creates a Pending extension request against a Confirmed booking the
    caller owns. requested_end_time must be after the booking's current
    end_time. If library_settings.extension_limit_minutes is set (see
    section 5.8), the requested extra time cannot exceed it - this is
    the first story to actually enforce that setting.
    Errors: 400 missing/bad time, booking not Confirmed, requested time
    not after current end, or extension exceeds the configured limit;
    404 booking not found or not yours; 409 an extension request is
    already Pending for this booking.
GET    /api/staff/extension-requests   (Staff or Admin)
    Body: none. Optional ?status= (defaults to "Pending"; pass Approved/
    Rejected to review resolved ones). Each entry is annotated with the
    booking's current end_time, seat_number, and the requesting
    student's full_name/username.
POST   /api/staff/extension-requests/<id>/approve   (Staff or Admin)
    Body (optional): { "seat_id": 6 }
    With no seat_id, tries to extend the booking on its current seat.
    If another Confirmed booking occupies that seat during the extra
    time, this returns 409 instead of silently failing - the staff
    member is expected to retry with a free seat_id to reassign the
    student instead (Story 3.7's "...or assign a new available seat").
    On success the underlying Booking row's end_time (and seat_id, if
    reassigned) is updated directly; the extension_request itself is
    marked Approved with approved_by set to the acting staff/admin.
    Errors: 404 request or seat not found, 400 request already
    resolved or booking no longer Confirmed, 409 seat clash.
POST   /api/staff/extension-requests/<id>/reject   (Staff or Admin)
    Marks the request Rejected, approved_by set to the acting user.
    Errors: 404 not found, 400 already resolved.

Overlap detection (used by booking creation/modification, seat
availability search, and extension approval alike):
    existing_start < new_end AND existing_end > new_start
This correctly blocks partial overlaps while still allowing back-to-back
bookings (one ending exactly when another starts).

5.12 CHECK-IN & ATTENDANCE (Story 4.1/4.2 - Staff or Admin)
POST   /api/staff/checkin
    Body: { "checkin_code": "" }
    Looks up the Confirmed booking with this checkin_code, creates an
    attendance row (checkin_time = now, verified_by = acting staff/admin),
    and flips the booking's status to "Checked-In". Booking status values
    are now "Confirmed" / "Checked-In" / "Cancelled" / "No-Show" /
    "Completed" (Checked-In added by this story, No-Show by Story 4.3,
    Completed by Story 4.4 - see sections 5.13/5.14 below).
    The booking must be dated today - this endpoint verifies a student
    physically arriving right now, so a checkin_code for a future advance
    booking is rejected until its date arrives. (No time-of-day window
    check here - that's Story 4.3's no_show_grace_minutes logic, see
    section 5.13.)
    Errors: 400 missing/empty checkin_code, 404 checkin_code not found,
    400 booking not Confirmed (already checked in, cancelled, etc.) or
    not dated today.

5.13 NO-SHOW MANAGEMENT (Story 4.3 - Staff or Admin)
GET    /api/staff/bookings/no-show-candidates
    Body: none. Lists every Confirmed booking whose slot (booking_date +
    start_time) is at or past library_settings.no_show_grace_minutes
    from now. If no_show_grace_minutes is unset (null), grace defaults
    to 0 - a booking becomes a candidate the moment its start_time
    passes. Response includes grace_minutes used and each candidate
    annotated with seat_number/full_name/username/minutes_overdue,
    sorted most-overdue first.
POST   /api/staff/bookings/<booking_id>/no-show
    Body: none. Marks a Confirmed booking No-Show once it's past the
    same grace cutoff used above, freeing its seat immediately (the
    same overlap queries that block double-booking only match
    status="Confirmed", so nothing else needs updating).
    Errors: 404 booking not found; 400 booking not Confirmed (already
    Checked-In/Cancelled/No-Show) or still within the grace period.

5.14 STUDY SESSION CHECK-OUT (Story 4.4 - own booking, or Staff/Admin)
POST   /api/bookings/<booking_id>/checkout
    Body: none. Closes out a Checked-In booking: finds its open (still
    checkout_time=null) attendance row, stamps checkout_time = now, and
    flips the booking's status to "Completed". Ownership rule matches
    PUT /bookings/<id> and POST /bookings/<id>/cancel - only the
    booking's own student, or Staff/Admin, may call this.
    The seat itself was already excluded from every overlap/
    availability query the moment check-in flipped status away from
    "Confirmed" (see section 15 item 11), so checkout doesn't need to
    do anything extra to "free" it - it only closes the attendance
    record and finalizes the booking's status.
    Errors: 404 booking not found (or, in the unexpected case a
    Checked-In booking somehow has no open attendance row, 404); 403
    not your booking; 400 booking not currently Checked-In (never
    checked in, cancelled, already checked out, etc.).

7. COMMON ERRORS AND FIXES
========================================================================

"Email is required" even though sent -> set Content-Type: application/json,
    Body tab set to JSON not Text.
401 Unauthorized on every request -> token missing/expired/no "Bearer " prefix.
403 not allowed -> wrong role's token used for that route.
sqlite3.OperationalError: no such column -> delete app.db, restart server.
ModuleNotFoundError: No module named 'flask_cors' -> pip install -r requirements.txt.
git push rejected (fetch first) -> git pull origin dev, then push again.

13. DATABASE SCHEMA (ERD SUMMARY)
========================================================================

TABLE: users
--------------------------------------------------------------------
Column          Type            Notes
user_id         Integer PK      auto-increment
username        String(100)     unique, required
password_hash   String(255)     hashed with Werkzeug generate_password_hash
email           String(150)     required
id_type         String(255)     optional (see Field Reference below)
id_number       String(255)     optional (see Field Reference below)
phone           String(20)      optional
role            String(20)      "Admin" / "Staff" / "Student"
status          Boolean         True = active account, False = deactivated

TABLE: membership_plans
--------------------------------------------------------------------
Column          Type            Notes
plan_id         Integer PK      auto-increment
plan_name       String(100)     "Weekly" / "Monthly" / "Yearly" (seeded)
duration_days   Integer         used to calculate membership_expiry on approve
price           Numeric(10,2)   editable via PUT /admin/membership-plans/<id>
is_active       Boolean         True by default; DELETE /admin/membership-plans/<id>
                                sets this False (soft-retire, not a real row delete -
                                added beyond dbSchema.docx since students.plan_id
                                still references retired plans and "retire" implies
                                soft-delete, not hard delete)

TABLE: students
--------------------------------------------------------------------
Column              Type            Notes
student_id          Integer PK      auto-increment
user_id             Integer FK      -> users.user_id (1-to-1 with a User row)
full_name           String(150)     required
address             Text            optional
membership_status   String(20)      Pending / Active / Rejected / Disapproved
plan_id             Integer FK      -> membership_plans.plan_id (nullable)
membership_expiry   Date            set automatically when Admin approves

TABLE: seats
--------------------------------------------------------------------
Column          Type            Notes
seat_id         Integer PK      auto-increment
seat_number     String(20)      unique, required (e.g. "A1")
seat_type       String(50)      optional, free text (e.g. "Standard") - not
                                validated against a fixed list
is_active       Boolean         True by default; False excludes the seat from
                                availability search/booking (see section 15
                                item 8 for why this replaced status)

Admin CRUD via POST/GET/PUT /admin/seats (Story 2.2). No DELETE route -
taking a seat out of service is done by setting is_active to false.
20 sample seats (S01-S20) are auto-seeded on first app run.

TABLE: bookings
--------------------------------------------------------------------
Column          Type            Notes
booking_id      Integer PK      auto-increment
user_id         Integer FK      -> users.user_id (the student who booked)
seat_id         Integer FK      -> seats.seat_id
booking_date    Date            required
start_time      Time            required
end_time        Time            required, must be after start_time
checkin_code    String(20)      unique, auto-generated (secrets.token_hex)
status          String(20)      "Confirmed" / "Checked-In" / "Cancelled" /
                                "No-Show" / "Completed", defaults to
                                Confirmed (Checked-In: Story 4.1/4.2,
                                No-Show: Story 4.3, Completed: Story 4.4
                                - this is now the full dbSchema.docx
                                booking_status enum, Booked-vs-Confirmed
                                naming drift aside, see section 15 item 8)
created_at      DateTime        set on creation

Managed via /bookings, /students/me/bookings, /staff/bookings/*,
/staff/checkin (Stories 3.1-3.7, 4.1-4.4).

TABLE: attendance
--------------------------------------------------------------------
Column          Type            Notes
attendance_id   Integer PK      auto-increment
booking_id      Integer FK      -> bookings.booking_id
checkin_time    DateTime        set when staff verifies the checkin_code
checkout_time   DateTime        nullable; set via POST
                                /bookings/<id>/checkout (Story 4.4)
verified_by     Integer FK      -> users.user_id, the staff/admin who
                                checked the student in

Created via POST /staff/checkin (Story 4.1/4.2), closed via POST
/bookings/<id>/checkout (Story 4.4). One row per successful check-in;
a booking can only be checked in once since the underlying
Booking's status leaves "Confirmed" the moment attendance is recorded,
and only Confirmed bookings are eligible for check-in.

TABLE: extension_requests
--------------------------------------------------------------------
Column                  Type            Notes
extension_request_id    Integer PK      auto-increment
booking_id              Integer FK      -> bookings.booking_id
requested_end_time      Time            the new end_time the student is
                                        asking for (dbSchema.docx models this
                                        as datetime; stored as Time here to
                                        match Booking.end_time's own type -
                                        see section 15 item 9)
status                  String(20)      "Pending" / "Approved" / "Rejected"
requested_at            DateTime        set on creation, used to order the
                                        staff queue oldest-first
approved_by             Integer FK      -> users.user_id, set on approve OR
                                        reject (whichever staff/admin acted)

Managed via /students/me/bookings/<id>/extension-request and
/staff/extension-requests/* (Story 3.7). Approving does not create a
new booking - it mutates the existing Booking row's end_time (and
seat_id, if the staff member reassigns to a different seat).

TABLE: library_settings
--------------------------------------------------------------------
Column                    Type            Notes
setting_id                Integer PK      auto-increment
open_time                 Time            set via PUT /admin/settings (Story 2.1)
close_time                Time            set via PUT /admin/settings (Story 2.1)
total_seats                Integer         not yet managed by any story - null
no_show_grace_minutes      Integer         managed by Story 4.3 - when set (non-
                                           null), a Confirmed booking becomes a
                                           no-show candidate this many minutes
                                           after its start_time; null defaults to
                                           0 (candidate as soon as start_time
                                           passes). No PUT /admin/settings
                                           support for it yet - only settable
                                           directly in the DB or a future admin
                                           route
cancellation_period        Integer         not yet managed by any story - null
max_booking_days_ahead     Integer         not yet managed by any story - null
extension_limit_minutes    Integer         managed by Story 3.7 - when set (non-
                                           null), caps how many extra minutes a
                                           student may request in one extension-
                                           request call. Still null/unenforced
                                           until an Admin sets it (no PUT
                                           /admin/settings support for it yet -
                                           only settable directly in the DB or a
                                           future admin route)
updated_by                Integer FK      -> users.user_id, set on every PUT
updated_at                DateTime        set on every PUT

Single-row table: one default row (09:00-21:00) is auto-seeded on first
app run in app.py:seed_data(). There is no POST/DELETE for this table -
Admin only ever edits the one existing row via PUT /admin/settings.

RELATIONSHIPS
--------------------------------------------------------------------
users (1) ----- (1) students        [every Student row links to one User row]
membership_plans (1) ----- (many) students  [many students can share one plan]
users (1) ----- (many) library_settings.updated_by  [tracks which admin last changed settings]
users (1) ----- (many) bookings     [a user can have many bookings over time]
seats (1) ----- (many) bookings     [a seat can be booked many times, never overlapping while Confirmed]
bookings (1) ----- (many) extension_requests  [a booking can accumulate multiple requests over time, only one Pending at once]
users (1) ----- (many) extension_requests.approved_by  [tracks which staff/admin resolved each request]
bookings (1) ----- (many) attendance  [in practice one per booking, since check-in is only allowed once per Confirmed booking]
users (1) ----- (many) attendance.verified_by  [tracks which staff/admin performed the check-in]

IMPORTANT: There is currently NO separate "memberships" table. The admin
membership routes (/api/admin/memberships/...) reuse student_id as the
membership_id. If your project brief requires a separate membership
history table (e.g. to track multiple past memberships per student),
this needs a new model - flag this with your team before final submission.

========================================================================
14. FIELD REFERENCE (WHAT EACH FIELD MEANS)
========================================================================

username           - login identifier, must be unique across all roles
password            - plain text on input only, stored as hashed password_hash
email               - contact email, required for all users
id_type             - type of ID proof submitted (e.g. "Aadhar", "College ID",
                      "Passport") - free text, not validated against a fixed list
id_number           - the actual ID proof number matching id_type
phone               - contact number, optional, no format validation currently
role                - controls access: Admin / Staff / Student (set by system,

membership_status   - one of: Pending, Active, Rejected, Disapproved
                      Pending    -> just registered, awaiting admin decision
                      Active     -> approved, has a valid membership_expiry
                      Rejected   -> admin rejected the pending request
                      Disapproved-> was Active, admin later disapproved it
plan_id             - links student to a MembershipPlan; can be null if no
                      plan chosen yet
membership_expiry   - calculated as today + plan.duration_days on approval;
                      can be manually extended/set via admin PUT route
duration_days       - defines how long a plan lasts once approved
price               - plan cost, editable by Admin only, stored as decimal
seat_type           - free text seat category (e.g. "Standard"), not validated
                      against a fixed list, purely informational for now
is_active (Seat)    - true = bookable, false = out of service (see section
                      15 item 8)
checkin_code        - auto-generated unique code returned when a booking is
                      created; will be what Epic 4's check-in flow verifies
                      against, once built

                      POST /bookings/<id>/checkout)
checkin_time        - set on the attendance row when staff verifies a

checkout_time       - set on the attendance row when the student (or

                      GET /staff/bookings/no-show-candidates
requested_end_time  - the new end_time a student is asking for on an

status                Pending  -> just submitted, awaiting staff decision
                      Approved -> staff extended the booking (same seat or
                                 reassigned to a different one)
                      Rejected -> staff declined the request; the original

15. DESIGN ASSUMPTIONS AND KNOWN LIMITATIONS
========================================================================

1. membership_id == student_id
   The admin membership routes assume one membership per student, so
   membership_id is just the student's student_id. There is no history
   of past memberships if a student re-registers after being rejected.

2. No password reset via email
   ResetPasswordResource requires the OLD password to be known. There is
   no "forgot password" flow (no email/OTP reset) implemented yet.

3. No refresh token
   Access tokens expire after 8 hours (JWT_ACCESS_TOKEN_EXPIRES in
   config.py) and the user must log in again - there is no refresh
   token endpoint currently.

4. No staff reactivation route, no plan un-retire route
   Staff can be deactivated (POST /admin/staff/<id>/deactivate) but
   there is no "reactivate" endpoint yet. Same gap for membership plans:
   DELETE /admin/membership-plans/<id> retires a plan but there is no
   route to set is_active back to true.

5. role is server-controlled
   The client should never send "role" in any request body - it is
   always set internally (Staff registration always creates role=Student,
   admin staff creation always creates role=Staff, etc). If a request
   body includes "role", it is currently ignored, not rejected - confirm
   this is acceptable for your project or add explicit rejection.

6. No pagination
   GET /admin/staff, GET /admin/memberships, GET /admin/membership-plans,
   GET /admin/seats all return the full list with no page/limit
   parameters. Fine for small datasets in a college project, but note
   this if scaling later.

7. SQLite only in dev
   config.py defaults to SQLite (app.db). For production or team-shared
   testing, DATABASE_URL env variable can point to Postgres/MySQL instead,
   but this hasn't been tested with this project yet.

8. Seat model uses is_active/seat_type, not dbSchema.docx's status field
   dbSchema.docx specifies seats.status as "Available"/"Maintenance".
   Two branches of this project independently built a Seat model: Epic
   2.2's used that status field; Epic 3's (seat availability/booking)
   used is_active (bool) + seat_type instead, and all the booking logic
   (availability search, clash detection, walk-in auto-assignment) reads
   is_active. When these were merged for Story 3.7, is_active/seat_type
   was kept as canonical - rewriting the booking code to match the
   schema doc instead would have touched far more logic across
   resources/bookings.py. Functionally equivalent: is_active=false means
   the same thing "Maintenance" did. Flag this drift from dbSchema.docx
   with the team; if it matters for grading/spec compliance, the fix is
   confined to resources/seats.py's admin endpoints.

9. extension_requests.requested_end_time is Time, not datetime
   dbSchema.docx models this column as datetime. It's stored as Time
   here instead, matching Booking.start_time/end_time's own type (bookings
   already split date and time into separate columns rather than using
   combined datetimes). Kept consistent with the existing Booking model
   rather than the schema doc's literal type.

10. no_show_grace_minutes defaults to 0 when unset
    Unlike extension_limit_minutes (Story 3.7), which is simply
    unenforced (no cap) until an Admin sets it, Story 4.3 treats a null
    no_show_grace_minutes as 0 rather than "no-show never applies" -
    the no-show endpoints are the entire point of that story, so they
    need to work without any DB setup. Confirm this default is
    acceptable, or set no_show_grace_minutes directly in the DB (no
    admin route exposes it yet - same gap as extension_limit_minutes).

11. A booking's seat is released at check-in, not checkout
    Every overlap/availability query (booking creation, modification,
    seat availability search, walk-in auto-assignment, extension
    approval) filters on Booking.status == "Confirmed". A booking
    already stops blocking its slot the moment Story 4.1's check-in
    flips it to "Checked-In" - well before Story 4.4's checkout flips
    it again to "Completed". Story 4.3's "mark no-show, release seat"
    and Story 4.4's "record checkout, free seat" wording both describe
    this same status-leaves-Confirmed mechanism, but for a Checked-In
    booking the seat was administratively free from check-in onward;
    checkout's role is closing the attendance record and marking the
    session finished, not the seat release itself.

16. ENVIRONMENT VARIABLES (OPTIONAL, FOR PRODUCTION SETUP)
========================================================================

config.py reads these from environment variables, with defaults if unset:

SECRET_KEY        - Flask session secret (default: "change-me-in-production")
DATABASE_URL      - SQLAlchemy DB URI (default: "sqlite:///app.db")
JWT_SECRET_KEY    - JWT signing secret (default: "jwt-change-me-in-production")

For local development, the defaults are fine and no .env file is needed.

For any real deployment, set these before running the app:

Windows (PowerShell):
    $env:SECRET_KEY="your-real-secret"
    $env:JWT_SECRET_KEY="your-real-jwt-secret"
    $env:DATABASE_URL="your-real-database-url"
    python app.py

Or create a .env file and load it with python-dotenv (not yet added to
requirements.txt - install python-dotenv and add load_dotenv() in
config.py if you want this).
